Customer performance diagnosis

A mock example. This shows why you would use these metrics. AgentX coding-agent sessions and synthetic chat traffic are replayed through the real Dynamo router and session index. The workers are mock workers: DeepSeek V4 Flash on B200 timing comes from AISimulate's perf model, and the cache tiers are set small on purpose to create each situation.

1. What is running, and how is it responding?

Throughput first, then the response time it gets. If time to first token and inter-token latency are low, there is little to fix.

3. How much of the cache could we be hitting?

The funnel branches in two places. The first gap is cache no worker holds, which points at capacity. The second is cache a worker holds that the request did not use, which points at routing.

Cache reuse funnelmetric: existing

Share of input tokens at each step, per minute. The top line is the prefix a returning session could reuse if nothing had been evicted. Agent histories only grow, so it sits near 100% except on first turns. The highest-cache worker is the one holding the most of this request's prefix; it is not necessarily chosen, because the router also weighs load. The chosen worker is the one it picked. Worker-reported reuse is what the worker says it served from cache when it admitted the request; it falls below the chosen worker's line when cache the router counted was evicted while the request waited.

Why the router passed over the highest-cache worker

From the router's per-request decision log (the router_selection trace), not from a metric. Each request records every candidate worker's cache and load. This explains the gap between the highest-cache worker and the chosen one.

How decisions related to cachelog: router_selection trace

Among the decisions where the workers held different amounts of this request's prefix. Decisions where every candidate held the same amount are left out and counted in the note below. Smoothed over five points.

Why it left the highest-cache workerlog: router_selection trace

Of the decisions that left the highest-cache worker, the share where the chosen worker had less load. A decision can count in more than one line; when none does, the pick came from other cost terms. Smoothed over five points.

4. Does the working set fit the fleet?

Demand is the distinct prefix the active sessions will present next, counting a shared block once. It is shown over several timescales against what the fleet can hold. A working set that fits on paper can still miss the cache, which is why the next section looks at how it is stored.

Demand over several timescalesmetric: new

Sessions active in the last few minutes, each block counted once, against GPU memory and GPU plus host memory. If workers hold copies of the same blocks the room needed is larger; the copies charts in section 5 show by how much. Only sessions inside the router's active window count (100 seconds in these replays, where think times are also shortened), so the 5 and 15 minute lines coincide here; with real think times and a 15 minute window they separate.

What the fleet holdsmetric: new

What is resident in GPU memory and in host memory, stacked, counting every worker's copy because each takes room, against the distinct demand and the capacity of each tier. Host memory is mostly a copy of what is already on the GPU, so the stack shows the host as a second full layer, but only the sliver labelled "host only" adds room beyond the GPU. The mock workers write host memory through, which exaggerates this; a real offload tier may differ.

Prefix rebuilt by returning sessionsmetric: new

Share of agent input tokens each minute that a returning session had to recompute or reload because its earlier prefix was no longer in cache. An estimate from the session index, not a worker measurement. Smoothed over a few samples.

5. How is the cache stored?

Redundant copies, overlap between GPU and host memory, uneven workers, state kept for sessions that are finished, and prefixes shared between sessions.

Redundant copiesmetric: new

Copies of the cache across workers within one tier. 1x means each block is on one worker; it cannot go lower. A high value early in a run is sessions moving between workers while caches are cold, and it falls as the caches fill with different sessions.

Is one worker holding more cache?log: session_worker_load

Distinct session tokens in the GPU of the busiest, the average and the least busy worker, against what one worker can hold. A busiest worker at its limit while the others have room means the cache is uneven, not short. Per-worker figures come from the per-worker log.

metric: new The same thing as a ratio, from the router's imbalance metrics: the busiest worker over the average worker, so 1.0 is even and a sustained value above about 1.5 is worth an alert.

What is in GPU memorymetric: new

Tokens the active sessions need, tokens left behind on a worker by sessions whose last turn ran on another, and tokens held for finished sessions. The last two are capacity the active sessions cannot use.

State kept for finished sessionsmetric: new

Distinct tokens held only for sessions that are no longer active. They are evictable, but they take room the active sessions may need.

Prefix shared between sessionsmetric: new

Prompt tokens that more than one active session presents, against the distinct demand. A large share would be worth keeping on every worker.
