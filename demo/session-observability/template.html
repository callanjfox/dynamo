Your sessions

What the workload looks like: how many turns a session runs, how large its prompts and outputs are, how fast its context grows, and how much it fans out into subagents.

Shape of the sessions

Number of sessions in each range, including subagents. Turns, prompt size per turn, and the largest context each session reached.

Request size over time

Mean input and output tokens per request in each 60 second window. Input grows as sessions accumulate context; output stays small.

Working set and cache

Is the working set larger than the cache, and what does that cost? Demand against capacity first, then the thrash it causes.

Working set against capacity

Demand is the distinct tokens the active sessions will present next. Resident is what each tier holds. A shared prefix is counted once in both.

Thrash: prefix tokens a returning session had to rebuild

Tokens per 30 seconds. Recomputed means the prefix was in no tier. Reloaded means it was only in host memory.

Active sessions

Sessions active inside the window, split into primary sessions and the subagents they spawn.

Primary sessions and subagents

The distinct working set split by role. A subagent counts only the blocks its primary sessions do not already hold, so its line is the capacity subagents add on top of the sessions that spawned them.

Demand if idle sessions decay

The same demand counting only sessions active in the last 30 seconds, minute or five minutes, against the longer active window. A session quiet for minutes may or may not return; the gap between these lines is demand that depends on that bet. The return-gap panel below shows how often sessions do come back.

KV held for idle or finished sessions

Distinct GPU tokens that only inactive sessions still reference. This is evictable, so it matters only when it crowds out active demand.

Agent traffic against the rest

Share of routed requests, and of input tokens, that carried a session ID, in each 60 second window. Everything else on this page describes only that share. Requests without an ID are routed as usual but are not tracked. The partial coverage run sends 30% of its sessions without headers.

Duplication factor

Copies of the cache across workers: 1x means each prefix block is held on one worker, 2x means on average two. It is the tokens held on workers divided by the distinct tokens, so it rises when the router spreads sessions that share a prefix.

Shared prefix across sessions

Prompt tokens that more than one active session presents, such as a system prompt, a repository summary, or a subagent starting from its parent's context. The per-session demand sum counts them each time; the distinct demand counts them once.

Load across workers

Demand homed on the busiest worker against what one worker can hold, and the mean. Fleet totals can look fine while a few workers carry most sessions and spill past their own GPU and host memory. The sessions are homed where their last turn ran.

Distinct session tokens each worker's cache holds, the busiest worker against the mean. A busiest worker pinned at capacity while the mean is low means the load is uneven.

Cache reuse funnel

Share of prompt tokens at each step in each 60 second window. The top line is what the session history says could be reused if nothing had been evicted (from the session index, covered traffic only); the steps below it are what the router and the worker find. F2 is the prefix the router estimates is cached on the best eligible worker. F3 is the same on the worker it chose. F4 is what the worker reports reusing. The table has the cumulative totals.

Where a returning session finds its prefix, by time since its last turn

Share of returning turns whose prior prefix was on the GPU, in host memory, or mostly missing (so recomputed), to within a tenth. Long gaps lose the GPU.

What the sessions look like

Distribution across all sessions in this run, including subagents. Context is the largest prefix a session presented.

Compute health

How the workers cope with that load. If the working set is too big the cost shows up here: longer time to first token as prefixes are recomputed, a queue building, the KV cache full. Latency and queue series come from the frontend and the router's per-worker load tracking. Workers are mockers, so absolute times are the simulation's.

Time to first token

Median and 90th percentile over a trailing 30 seconds. Prompts that recompute a large prefix wait longer for their first token.

Inter-token latency

Median and 90th percentile over a trailing 30 seconds, in milliseconds. It rises with batch size and context length.

Queues

Requests the router has booked on a worker and not yet marked prefill-complete (waiting for the prefill or running it), requests decoding, and requests held at the frontend or router queue before dispatch. A growing prefill count means the fleet is saturated.

Estimated queue wait

Prefill backlog (prompt tokens queued or being prefilled) divided by the input token rate over a trailing 30 seconds: how long the backlog takes to clear. Neither the frontend nor the mock workers export a queue-time histogram, so this is derived. A real engine exports one (vllm:request_queue_time_seconds) and it should replace this estimate.

KV blocks in use per worker

Share of each worker's GPU KV blocks booked by its active requests, from the router's load tracking. A worker near 100% is full; an uneven spread means the router is concentrating sessions.

Metric reference

Every metric on this page. Session metrics are the ones added in this work. All carry the router_ prefix, are experimental, and use only bounded labels: no session or tenant ID is ever a label. Per-session detail goes to the dynamo_session_summary log.

Synthetic workload, not a customer trace. Time is simulated. Active means the session had activity within 5 minutes and has not ended. Thrash is estimated from the prior turn's input plus output against what the index holds, so it carries up to one block of rounding per turn.
