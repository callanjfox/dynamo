Request size over time

Working set and cache

Is the working set larger than the cache, and what does that cost? Demand against capacity first, then the thrash it causes.

Working set against capacitynew

Demand is the distinct tokens the active sessions will present next. Resident is what each tier holds. A shared prefix is counted once in both.

Thrash: prefix tokens a returning session had to rebuildnew

Tokens per 30 seconds. Recomputed means the prefix was in no tier. Reloaded means it was only in host memory. This is an estimate, not a worker measurement: when a returning turn arrives the router takes the previous turn's input plus output as the prefix the session should find, and subtracts what the session index says each tier still holds for that session. The worker-reported reuse (funnel step F4) would be the measured counterpart; the mock workers do not report it.

Active sessionsnew

Sessions active inside the window, split into primary sessions and the subagents they spawn.

Primary sessions and subagentsnew

The distinct working set split by role. A subagent counts only the blocks its primary sessions do not already hold, so its line is the capacity subagents add on top of the sessions that spawned them.

Demand if idle sessions decaynew

The same per-session demand counting only sessions active within each window, against the router's active window. A session quiet for minutes may or may not return; the gap between these lines is demand that depends on that bet. The return-gap panel below shows how often sessions do come back.

KV held for idle or finished sessionsnew

Distinct GPU tokens that only inactive sessions still reference. This is evictable, so it matters only when it crowds out active demand.

Agent traffic against the restnew

Input and output tokens per second (60 second window) from requests that carried a session ID, stacked on those that did not. Everything else on this page describes only the session share. Requests without an ID are routed as usual but are not tracked. The partial coverage run sends 30% of its sessions without headers.

Duplication factornew

Copies of the cache across workers, within one tier. 1x means each prefix block is held on one worker; 1.2x on the GPU line means the GPUs together hold 20% more blocks than there are distinct blocks, because some blocks sit on more than one worker. The host line is the same for host memory. It says nothing about whether host memory repeats what is on the GPU: the stacked chart above separates that when the run reports the overlap.

Shared prefix across sessionsnew

Prompt tokens that more than one active session presents, such as a system prompt, a repository summary, or a subagent starting from its parent's context. The per-session demand sum counts them each time; the distinct demand counts them once. In the AgentX corpus the sharing is small: sessions share nothing with each other, and a subagent's context is small next to its parent's, so the spikes are subagents starting. Traces with a common system prompt or repository would show much more.

Load across workersnew

Distinct demand homed on the busiest, the least busy and the mean worker, against what one worker can hold. A shared block counts once per worker. Fleet totals can look fine while a few workers carry most sessions and spill past their own GPU and host memory. A session is homed on the worker that served its last turn.

What the busiest worker actually holds, GPU and host stacked (host memory may also hold copies of GPU blocks, which the fleet-level overlap shows). A worker at the top of the stack is full.

Cache a worker still holds for active sessions whose last turn ran elsewhere: the cost of moving a session. It stays until evicted and is reusable if the session or another with the same prefix returns.

Routing decisionsnew: candidate inputs

Why the router picked the worker it did, from its per-candidate trace (router_selection records), per 60 second window. The router scores each worker on the cache it would reuse and on the load already there, and picks the lowest cost. The first chart splits decisions by how the pick related to cache; the second, for the decisions that left the worker with the most cached tokens, compares the cache given up with the load avoided. When the load avoided is as large as the cache given up, the router did what you would expect: it traded a cache hit for a less busy worker.

From the router's per-candidate cost trace, per 60 second window. This run recorded costs only, not the cache and load behind them, so it shows ties and how concentrated the picks were; the newer runs explain each pick.

Cache reuse funnelnew session-history line

Share of prompt tokens at each step in each 60 second window. The session-history line is what the session index says a returning session could reuse if nothing had been evicted (covered traffic only, and only the part that is a returning session's own prior prefix). F2 is the prefix the router estimates is cached on the best eligible worker. F3 is the same on the worker it chose. F4 is what the worker reports reusing. The table has the cumulative totals.

Where a returning session finds its prefix, by time since its last turnnew

Share of returning turns whose prior prefix was on the GPU, in host memory, or mostly missing (so recomputed), to within a tenth. A turn is counted when its request arrives, by the time since that session's previous turn finished: a session that waits ten minutes lands in "5 to 15 min" when it comes back, and one that never returns is never counted. The buckets (1, 5 and 15 minutes) are the same windows the decay chart uses. Long gaps lose the GPU.

What the sessions look likenew

Distribution across all sessions in this run, including subagents. Context is the largest prefix a session presented.

Compute health

How the workers cope with that load. If the working set is too big the cost shows up here: longer time to first token as prefixes are recomputed, a queue building, the KV cache full. Latency and queue series come from the frontend and the router's per-worker load tracking. Workers are mockers, so absolute times are the simulation's.

Time to first token

Median and 90th percentile over a trailing 30 seconds. Prompts that recompute a large prefix wait longer for their first token.

Inter-token latency

Median and 90th percentile over a trailing 30 seconds, in milliseconds. It rises with batch size and context length.

Throughput

Input tokens (left axis) and output tokens (right axis) per second the fleet serves, from the frontend's counters over a trailing 60 seconds. Input tokens are mostly cache hits when reuse is high, so a worker's real prefill load is lower. Two axes, so compare the shapes, not the heights.

Slowest worker against the median worker

The most recent time to first token (top chart) and inter-token latency (bottom chart) each worker reported: two different latencies, each shown for the slowest worker and the median worker. A wide gap means some workers are slower than others, which points at uneven load more than at the fleet being too small.

Queues

Requests the router has booked on a worker and not yet marked prefill-complete (waiting for the prefill or running it), requests decoding, and requests held at the frontend or router queue before dispatch. A growing prefill count means the fleet is saturated.

Estimated queue wait

Prefill backlog (prompt tokens queued or being prefilled) divided by the input token rate over a trailing 30 seconds: how long the backlog takes to clear. Neither the frontend nor the mock workers export a queue-time histogram, so this is derived. A real engine exports one (vllm:request_queue_time_seconds) and it should replace this estimate.

Metric reference

Every metric on this page. Session metrics are the ones added in this work. All carry the router_ prefix, are experimental, and use only bounded labels: no session or tenant ID is ever a label. Per-session detail goes to the dynamo_session_summary log.

Synthetic workload, not a customer trace. Time is simulated. Active means the session had activity within 5 minutes and has not ended. Thrash is estimated from the prior turn's input plus output against what the index holds, so it carries up to one block of rounding per turn.
